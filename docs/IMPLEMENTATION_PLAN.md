## 1. このリポジトリの目的

このリポジトリでは、AIエージェントファームの2体目の試験エージェント
「ドパバエ」（Dopabae）を開発する。

ショウジョウバエのコネクトームを LIF ニューロンで動かし、15分足のチャート画像を
「目」に見せて、その反応を売買の**方向**（近づく／逃げる／どちらでもない）に使う。
数量・価格・上限・諦めは決定的コード（檻）が担い、ペーパートレードで運用する。
**実取引は行わない。現物のみを扱う。**

儲けることが目的ではない。目的は次の2つ（設計メモ 1 章）。

1. 重み固定のハエの反応が、ランダムと区別できる偏りを持つか観察する
2. 報酬学習（ドーパミンによる可塑性）を足したとき、挙動がどう変わるか観察する

## 4. 責務の分離

以下の責務を混同しない。

### ハエ脳（シミュレーション）

チャート画像を受け取り、LIF シミュレーションを回し、接近側・回避側の
ニューロン群の発火数を返す。**ここは売買を知らない。** 残高・損益・保有量は見せない。

### 読み出し（発火率 → 方向）

「接近の指標 − 回避の指標」の1本の軸を閾値で三値（`APPROACH` / `AVOID` / `NONE`）に
落とす。設計者が決めた読み替え。閾値・対象ニューロン・神経時間は `agent.yaml` に置く。
ハエが書き換えない。「ハエの脳に売買を判断する細胞がある」という意味ではない。

### 方向の出どころ（`direction.source`）

方向を返すものは差し替えられる。ハエ版のほかに、評価用の「常時 `APPROACH`」と
「ランダム」を持つ。どれも同じ契約（入力：観測、出力：方向と根拠）を満たす。
返せなかった・読めなかったときは `direction.on_failure`（既定 `hold`）に従う。

### 檻（決定的コード）

方向を受け取り、数量・価格・建玉上限・現金比率・クールダウン・保有上限・
ドローダウン停止を `agent.yaml` の値で決めて、取消と発注を組み立てる純関数。
ハエがどう答えても最悪ケースはここで決まる。I/O を持たない。

### 報酬と可塑性

決済が確定した回だけ、確定損益から報酬（PAM11）/ 嫌悪（PPL101）の刺激を決める。
変わるのは KC→MBON のシナプス重みだけ。報酬の閾値は `agent.yaml`。

### 評価

固定版・学習版・檻だけ・ランダムを同じ物差しで比べる。
これが揃うまで「学んだ」とは言わない（設計メモ 4 章）。

### Phase 1：檻と方向インタフェース

ナンピノニクスの `config` / `cli` / `observe` / `state` / `orders` / `journal` / `run` を
本リポジトリへ**コピーして**持ち込み、`decide.py` を檻に置き換える。
ナンピノニクスの `veto.py` は持ち込まない。

#### 決めたこと

| 項目             | 決定                                                                  |
| ---------------- | --------------------------------------------------------------------- |
| 持ち込み方       | コピー。共通ライブラリ化しない（`REPOSITORY_PLAN.md`「扱わないもの」2） |
| 方向の契約       | 入力：観測（画像または事実）／ 出力：`APPROACH` / `AVOID` / `NONE` と根拠 |
| 最初の出どころ   | 「常時 `APPROACH`」と「ランダム」（`agent.yaml` の `direction.source`）。ハエ版は Phase 3 |
| 失敗時           | `direction.on_failure`（既定 `hold`）。出どころの種類によらず同じ     |
| 檻の入力         | 方向、観測、現在状態。出力は「何を取り消し、何を発注し、なぜそうしたか」 |

#### 後半で決めたこと（2026-09-16）

実機で 1 周したときの画像（15分足 8 本、スプレッド 1 円）を見て分かったこと。

**1. 買い気配の線が売り気配の線に隠れる**

スプレッドが 1 円だと、両方が同じ画素の行に落ちる。いまは買い気配（青）を先に、
売り気配（橙）をあとに描くので、**青が完全に消える。**

これは描画の見た目の問題ではない。**R8 は青と緑を受け取る担当**なので、
青い線が消えると、その入力がまるごと失われる。BTC/JPY のスプレッドが常にこの程度なら、
青は毎回消えることになる。

| 案 | 中身 | 難点 |
| --- | --- | --- |
| 1 | 描く順を逆にして青を勝たせる | 今度は橙が消える |
| 2 | 重なるときだけ 1 画素ずらす | **データに無い差を描く**ことになる |
| 3 | そのままにする | 青がまるごと消える |
| **4** | **重なった行は両方の色を混ぜる** | 配色に無い色が 1 行だけ現れる |

**4 を採った。** 同じ場所を 2 本が占めているなら、そこから届く光は 2 色の混合である。
これは描画の都合ではなく、画像が表しているものの素直な帰結である。青の寄与は
比例して残り、スプレッドに対して跳ばずに変わる。1 と 3 は入力を 1 つ捨てることになり、
2 はその解像度に無い差を描くことになる。

混色は `vision._mix` が採る 2 色の平均で、新しい設定値は増やしていない
（`agent.yaml` の `bid` と `ask` から決まる）。

**測った効果。** 実データに近い格子（37×37、R1–R6 が 8,214 個、R8 が 1,369 個）で、
スプレッド 1 円の画像を作って比べた。

| 確かめたこと | 結果 |
| --- | --- |
| 混色が入力に届いているか | 青を消すと **1,369 個中 37 個の R8 の値が変わる**。混色はこの入力を残している |
| 気配が入力に届いているか | 気配だけを動かすと 1,369 個中 44 個の R8 の値が変わった |

#### 座標表で分かった、まだ決めていないこと

**1. 左右の眼が画像の同じ場所を見ている**（2026-10-05、既定を Stonkfly の `split_eyes` にした）

カラム座標は左右の視葉で同じ値の範囲を使い、しかも**鏡像の関係にある**
（Mi1・T1 の細胞体の位置と座標の相関を見ると、左右で x 方向の符号だけが逆になる）。
いまの `retina.py` は左右を区別せずに置くので、**左眼と右眼の同じ座標のカラムが、
画像の同じ範囲を受け取る。** 入力は左右対称になる。

接近／回避の読み出しは左右の差を使わない。左右の差を使う読み出し
（Stonkfly の左右 DNp20 の差など）を腕にするなら、これが効く。

| 案 | 中身 |
| --- | --- |
| いま（既定） | 両眼に同じ画像を、同じ座標で見せる |
| 分ける | 画像の左半分を左眼、右半分を右眼に見せる（座標表に左右の列が要る） |
| 片眼 | 右眼だけを使う（R1-R6 が多いほう） |

**2. R1-R6 は左眼が右眼の半分しかない**

座標ありで左 1,107 / 右 2,236。調査でも「右視葉中心」と報告されていた
（[`CONNECTOME_SURVEY.md`](CONNECTOME_SURVEY.md) 2 章）。**原因は確かめていない。**
ラミナの L1・L2 は左右ほぼ同数（約 880 個ずつ）あるので、ラミナが欠けているせいではない。
入力の量が左右で違うことは、左右の差を使う読み出しを採るときの交絡要因になる。

**3. R8_unclear（442 個、うち座標あり 436 個）を使うか**

p / y が決まっていない R8。`blue_green_mean` なら同じ値を渡せるが、
`blue` / `green` の腕では型から決められない。いまは使わない（Stonkfly の 811 個と揃う）。

**4. R8 を型ごとに青と緑へ分けるか**（2026-10-05、既定を Stonkfly の `by_subtype` にした）

`R8p` は Rh5（青）、`R8y` は Rh6（緑）というのが文献の知見である（データには書かれていない）。
分けるなら `r8_channel` に型ごとの選択肢を足す。Phase 4 の腕として扱う。

#### 文字を見せるかどうか（2026-09-16 の実データから出た論点の 2 つめ）

ハエは字を読めないが、`BTC_JPY` と気配の数字は画素として入力される。
価格が変われば模様も変わるので、**意味のない変動が混ざっている可能性がある。**

Stonkfly も同じもの（ペア名と気配）を見せているので、いまは合わせてある。
測るなら Phase 4 で「文字なしの腕」と比べる（7 節）。

##### 経緯

最初は `status` が Traced の細胞とポアソン入力で組んだ。計算時間は上限に収まったが、

そこで 12 項目すべてを Stonkfly に合わせた（2026-10-05 に人間が決めた）。

**違いとして残したもの:** 最多のカラムが同数で並んだ光受容細胞には値を作らない（R1-R6 で 1 個）。

##### Stonkfly 本体と突き合わせた

Stonkfly（コミット `78ef3e0`）の神経部分だけを手元で、Stonkfly 自身の手順で動かした
（取引のコードは読み込んでいない）。作った配列は、Stonkfly 同梱のロックファイル 11 項目すべてと一致した。
そのうえで合成のチャートを 0.5 秒ずつ 2 回見せた。

| 確かめたこと | 結果 |
| --- | --- |
| 網（細胞・結合の並び・行き先） | **完全に一致。** 重みは R8 → aMe12 の 390 本だけ違う（Stonkfly は実行時に、こちらは網を作るときに正にする。どちらも 390 本） |
| 光受容細胞が見る画素と明るさ | R1-R6 の 3,334 個・R8 の 811 個すべてで同じ画素。明るさの差は 4×10⁻⁸ 以下 |

計算を飛ばすので、浮動小数点の丸めかたが違う。その差が点火の時刻を動かしうる。

##### 分かったこと：光受容細胞 1 個で、KC の発火が 100 倍変わる

こちらは同数で並んだ 1 個の R1-R6 に値を作らない。**入力の違いはこの 1 個（4,146 個中）だけ**なのに、

| | KC の発火（1 回目 / 2 回目） |
| --- | ---: |
| ドパバエ（その 1 個に入力なし） | 14 / 11 |
| Stonkfly（その 1 個に入力あり） | 1,533 / 4,839 |

差は、**嗅覚の局所細胞 lLN1_bc の回路に火が付くかどうか**で生まれていた。lLN1_bc どうしは
強く興奮させ合う（自分たちへの結合が合計 23,888 mV 相当）ので、一度火が付くと燃え続ける。
火が付くと、嗅覚の受容細胞（ORN）・投射細胞（PN）を経て KC が発火する。
シナプス数の閾値を 5 にすると、ドパバエの入力のままでも火が付いた（KC 2,319 / 3,804 / 3,803）。

**画像の中身とは関係なく、網のわずかな差で点火が決まる。** KC の発火を「画像に対する反応」と
読むと、この点火を見誤る。読み出しのニューロン群を選ぶときと、Phase 4 の評価で必ず確かめる
（[`CONNECTOME_SURVEY.md`](CONNECTOME_SURVEY.md) 7 章）。

##### 計算時間（Linux x86_64・4 コア・Python 3.11・numpy 2.4）

状態を引き継いで 3 回続けた。1 観測（神経時間 0.5 秒・5,000 刻み）あたり。

| 閾値 | 負荷なし（1 / 2 / 3 回目） | 背景 20 Hz の負荷試験（1 / 2 / 3 回目） |
| --- | --- | --- |
| なし | 6.3 / 6.8 / 7.0 秒 | 17.1 / 16.3 / 15.6 秒 |
| 3 以上 | 6.1 / 8.3 / 8.6 秒 | 14.9 / 16.8 / 16.1 秒 |
| 5 以上 | 6.3 / 7.3 / 8.6 秒 | 14.1 / 14.4 / 13.6 秒 |

- **どの条件でも `runtime.max_runtime_sec`（120 秒）に収まった。** 全脳のままでよい（この計算機では）
- 同じ画像で Stonkfly（C++・事象駆動）は 2.2〜5.2 秒。こちらは numpy で 2〜3 倍遅いが、C++ は要らない
- 網の変換は初回だけ 23 秒・2.2 GB。以後はキャッシュ（約 200 MB）を 0.1〜1.4 秒で読む。実行時のメモリは 0.5 GB
- 背景の負荷試験は全細胞へのポアソン入力で、**モデルの選択ではない**
- 閾値で変わる計算時間は 2 割ほど。閾値は性能ではなく、点火のしやすさなどの挙動で決めることになる
- 同じ入力・同じ状態からは同じ発火数が出る（2 回の計測で 394,941 回で一致）

  灰色＋上下反転で 3 型、0.02 で 5 型、0.02 の灰色で 1 型。腕どうしで 1 型も重ならない
- 読み出しの候補（群）は、ほとんどの腕で画像による差も上げと下げの差も p > 0.05 だった。例外は `fly-hs1` の DNa02（画像 0.045）・
  MDN（画像 0.009）と、0.02 の灰色の DNp20（上げと下げ 0.037）で、どれもほかの腕では p > 0.05。LC4・LPLC2・DNp01・DNp09 は発火しなかった

**まとめ（数字の言い直し）。** 静止画で見えていた上げと下げの差は、0.02 では配色、1.0 では光受容細胞の上への偏りで
説明がついた。どちらを外しても、視葉の外に上げと下げを分ける型は現れなかった。1.0 で視葉の外へ届いていた画像の差も、
格子の上下の向きを変えるとほぼ消えた。どれを採るかは人間が決める。

### Phase 4：評価（固定版）

設計メモ 4 章の評価 1・3・4 を回し、固定版の挙動と偏りを記録する。

| 評価 | 内容                                                     | 本 Phase |

| 4    | 同じ頻度でランダムに `APPROACH` / `AVOID` を出す対照群との比較 | **回す（最重要）** |

#### 決めたこと

- 評価は同じ期間の15分足で行い、成績の物差しはナンピノニクスの `performance.py` 相当
  （総資産の推移・ドローダウン・Buy&Hold 比較）を流用する
- ランダムの `APPROACH` / `AVOID` / `NONE` の頻度は、固定版が同じ期間に出した頻度に合わせる
- 固定版の偏り（いつも `APPROACH`、いつも `AVOID`）を先に測る。
  偏りがあれば、それは市場の洞察ではなくネットワークの癖として記録する
- 儲かったかではなく、**ランダムと区別できるか**を見る

#### 腕を並べる（replay はしない）

評価 3・4 は**腕（arm）どうしの比較**で行う。腕とは、方向の出どころだけが違う設定のこと。

過去の足を使った replay（再実行）は**しない。** `bitbank paper` の約定判定を自前で真似ると、
真似が本物とずれた分だけ評価が嘘になる。代わりに、腕ごとにペーパー口座の状態ファイルと
判断ログを分け、同じ生の相場を見ながら同時に走らせる。

```bash
python3 scripts/make_arm.py cage-only --source always_approach
python3 scripts/make_arm.py fly       --source fly
# ハエの頻度が出たら、その値を写してランダム対照群を作る
python3 scripts/make_arm.py random --source random --seed 20260915 \
  --weights '{"APPROACH":0.5,"AVOID":0.2,"NONE":0.3}'

python3 -m dopabae.run --config arms/fly.yaml    # 腕ごとに15分おき
python3 -m dopabae.evaluate --config arms/fly.yaml --config arms/random.yaml
```

`arms/` は生成物で Git 管理外。正本は `agent.yaml` であり、腕は方向の出どころと
置き場所だけを差し替える。檻とリスクの値は正本と同じにする。違えば、腕の差が
方向の差でなくなる。

#### 測るもの

| 何を                 | なぜ                                                         |
| -------------------- | ------------------------------------------------------------ |
| 方向の頻度と偏り     | いつも同じ方向なら、相場の洞察ではなくネットワークの癖         |
| 檻の扱いの内訳       | 方向が壁で消えているなら、成績の差は方向の差ではない           |
| 方向のあとの値動き   | `APPROACH` のあとと `AVOID` のあとで違わなければ、方向に情報がない |
| 成績                 | 総資産・最大ドローダウン・Buy&Hold 比較                        |

方向のあとの値動きの差には**並べ替え検定**を当てる。分布を仮定せず、種を固定するので
同じ入力なら同じ p 値が出る。標本が各 30 件に満たないうちは `sample_warning` を添え、
その差は偶然と区別できないと明記する。

ランダム対照群の頻度は、比べる相手が同じ期間に出した頻度に合わせる
（`matched_random_weights` がその値を出す）。頻度が違う対照群と比べると、
方向の**中身**の差ではなく頻度の差を見てしまう。

**`evaluate.py` は結論（`verdict`）を書かない。** 数字を出すだけで、
「学んだ」と言えるかは人間が判断する。

## 6. 定期運用と記録

15分ごとの定期実行は実装済み（`scripts/run_arms.py` と `scripts/launchd/` / `scripts/systemd/`）。
腕は**並行して**回す。順番に回すと、遅い腕のぶんだけ後ろの腕がずれた相場を見るため。

同じ腕の二重起動は `dopabae/lock.py` が `flock` で防ぐ。前の回がまだ走っていれば
その腕はこの回を飛ばす。ハエのシミュレーション（Phase 3）が入ると 1 回が長くなるので、
この守りが要る。腕ごとに上限（既定 600 秒）を置き、超えた腕は打ち切る。
打ち切られた腕はプロセスが死んでロックも外れ、次の回はやり直せる。

配線図が決まるまでは、**檻だけ**と**ランダム**の腕を回しておける。Phase 4 の評価 3・4 の
対照群が、ハエ版ができる前から貯まる。

判断ログには、ナンピノニクスの項目に加えて次を残す（設計メモ 3.6 節）。

- 見せた画像のハッシュと描画に使った足の範囲
- 接近側・回避側のニューロン群の発火数と、方向の根拠
- ハエの答えと、檻がそれをどう扱ったか
- その回に与えたドーパミン刺激（なし / 報酬 / 嫌悪）と根拠になった損益
- シナプス重みのスナップショット（一定間隔）

ハエの反応は観測値なので、そのまま書く。解釈は記録の言語化に閉じ込め、
判断ログには書かない。
